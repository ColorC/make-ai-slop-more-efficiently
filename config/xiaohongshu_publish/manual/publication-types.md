# 小红书发布类型

发布类型用于固定读者问题、资料来源、文章结构、载体和连续发布 Agent。一次 brief 只选一种类型。需要同时回答多个问题时分篇。

这些类型只约束内部制作流程，不代表账号对外承诺固定栏目，也不能写成“以后只发几类内容”。

## 标题与开头通则

- 写作批次同时生成 8 至 12 个标题候选，再按忠实、清楚、值得点开、平台自然度四项选择。
- 标题通常控制在 10 至 20 个汉字附近；具体对象、动作、结果或问题优先，抽象体系名与范围清单后置。
- “大家好、本人是、今天分享”不承担标题；职业身份仅在确实构成正文核心经验时进入标题。
- “X 系统与 N 个修正案例”“全流程方案、架构说明、能力建设”等内部文档式标题需要重写成人能立即理解的场景或问题。
- 数字、时间、失败反差和结果必须有正文证据。
- 开头前 1 至 3 句先交付结果、冲突、场景或读者问题，再补背景。

## 标题与封面必须成对设计

标题候选不能脱离首图单独评审。每个候选方案必须同时填写四项：

1. 标题：在信息流中说明具体对象、发生的事情或读者问题。
2. 封面视觉主体：优先使用真实页面、产品界面、Git diff、运行结果、工作现场或前后对照。
3. 封面主文字：只负责指出该证据最值得看的冲突或结果，不照抄标题。
4. 信息分工：分别写清读者从标题和封面各新增知道了什么；两项答案相同则方案退回。

标题研究必须围绕本篇的具体冲突展开，例如“AI 编造内容后撤回”“摘要丢失语境”“多 Agent 相互等待”；禁止只调研“小红书常见标题”“爆款公式”或通用字数。优先查看一组带日期的当前小红书搜索结果或真实笔记样本；平台样本不足时，再查开发者博客、论坛、视频和产品复盘中的相邻题材。研究记录必须保存原始标题、URL、它承诺的具体事情和它触发的读者处境，不能把营销课程当成个人经验帖的正面样本。

标题候选应从真实案例的后果、付出、矛盾或未解问题中产生。只说“系统、方案、历程、探索、问题在哪里”而没有具体对象与发生的事情，视为内部目录名，不能进入封面制作。

连续系列允许使用固定系列名加全角序号，例如 `AI发帖踩坑录（1）`。这种标题负责建立栏目识别和阅读预期，具体事件由封面主文字与开头第一段交付。系列名必须使用普通读者能立即理解的动作和处境；内部项目名、管线名、架构名不能充当系列名。已经采用固定系列名后，不再给每期标题追加长副标题。

同类选题首次制作前，还应保存可核验的标题与首图配对。网页无法回读首图时要明确记录证据缺口，不能凭第三方“爆款公式”宣称已经掌握平台规律。

封面候选至少提供三种有不同视觉主体的方案供审阅，不能只替换标题文字或背景颜色。能够公开的真实证据优先；纯大字卡只在没有合适视觉证据，且文字本身就是内容对象时使用。

最终在手机尺寸的信息流网格中同时检查：第一眼能否识别对象、封面小字是否仍可读、标题是否被截断、标题与封面是否重复、整组主页是否连续出现相同模板。

## 账号置顶介绍 `account_pinned_intro`

- 读者问题：这个账号是谁在运营，会发布什么，AI 内容如何识别。
- 内容边界：允许保留人类原文并由 AI 续写后半部分；内部记录两部分来源，AI 续写部分不叠加分隔声明，整篇正文首行保留唯一 Agent/Model tag；不承担完整技术架构或开发路线。
- 默认内部 Agent：`technical_publisher`。公开叙述采用发布 Agent 自己的视角，ColorC 始终为第三人称。
- 载体：普通图文。

## 技术介绍长文 `technical_introduction_longform`

- 读者问题：这是什么，现在由哪些部分组成，怎样运行，当前效果与边界是什么。
- 默认内部 Agent：`technical_publisher`，连续身份纸鸢；正文首行保留唯一的纸鸢与最终成文模型 tag。
- 资料来源：当前代码、操作手册、真实运行结果、公开页面与截图。
- 时间边界：只描述当前有效设计。旧方案、踩坑和修改过程进入路线帖。
- 载体：长文；图片按阅读顺序插入对应章节。
- 当前接口：成熟套件可以填写长文与核验平台 AI 标识；浏览器真实发送已由传输策略暂停，管线必须停在预览态。

推荐章节：

1. 一句话定义：对象、服务谁、目前能做到哪一步。
2. 使用边界：输入、输出、公开授权与人工审阅位置。
3. 系统组成：资料层、写作层、检查层、视觉层、审阅台与发送连接器。
4. 运行流程：选择一个完整发布用例，按动作顺序解释组件怎样协作。
5. Agent 与连续性：公开身份、SOUL、Memory、工作手册各自承担什么。
6. 可见效果：真实页面、预览稿、运行回执或测试结果。
7. 接口和限制：当前支持的载体、未接通部分、失败时怎样停下。

图片规则：

- 定义之后放真实成果总览。
- 架构章节使用可独立阅读的结构图。
- 运行章节优先放真实审阅页、网页、终端输出或流程证据。
- 图片前告诉读者要看什么，图片后用一句图注说明它证明什么。
- `content_blocks_file` 按 `text → image → text` 保存真实阅读顺序。

文风参考：成熟工程博客、开发者个人主页和软件架构说明。开头先交代读者与问题，逐层展开边界、组件和运行场景。术语首次出现时就近解释。说明已知限制，不添加无法核验的效果。

## 踩雷路线图文 `journey_retrospective_carousel`

- 读者问题：这件事怎样做出来，经历了哪些关键转变，发现了什么。
- 默认内部 Agent：`journey_publisher`，连续身份砚青；正文首行保留唯一的砚青与最终成文模型 tag。
- 资料来源：Omnicompany 统一决策叙事缓存及每个事件指向的证据。
- 载体：普通图文；正文提供连贯说明，图卡承担关键转变、真实证据和前后对照。

固定取材流程：

1. 涉及个人网站、内部文章、demogame 与小红书等多条发布管线时，先运行一次 `omni decisions narrative --mode scope --scope outward-publishing --deterministic --force`。只写单个项目时才使用 `--mode project -p <project>`。
2. 后续帖子直接读取同一缓存，不重新扫描全部发布页或原始会话。缓存是统一决策库的可重建投影，事实修订仍写回决策记录。
3. 一篇选 3 至 6 个节点。每个节点必须有事件 ID 和可回看的证据。
4. 展开每个节点：当时在做什么、采用了什么做法、出现了什么具体问题、怎样修正、现在怎样处理、读者可复用的经验。
5. 删除只能构成时间流水的节点，也删除无法展开的内部缩写和数字。

公开叙述采用发布 Agent 自己的视角。AI 对材料的归纳必须忠实、有来源，且整篇仍需开启平台 AI 内容标识。

正文顺序：

1. 当前结论：先告诉读者这条路线现在走到了哪里。
2. 起点与约束：只补理解后文所需的信息。
3. 关键转变：按因果顺序展开，不要求按日期穷举。
4. 重复错误：说明它为什么反复出现，以及管线里新增了哪项可验证动作。
5. 当前做法与未解问题：明确哪些已经固化，哪些仍在实验。

## 纯文本的视觉层级

无格式正文允许使用以下元素：

- 单独一行的短标题；
- 段间空行；
- `01 / 02 / 03` 等顺序编号；
- `·`、`—` 等普通文本项目符号；
- 少量承担导航作用的符号。

正文不能依赖 Markdown 标题、粗体、链接语法、代码围栏或 HTML 才能成立。标题与符号服务阅读层级，不能代替具体解释。
