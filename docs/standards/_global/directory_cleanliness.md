# 目录清洁度守则

> 适用范围：从 C:/workspace/ 发起的文件治理及纳入 Guardian 的项目。2026-09-07 按用户要求统一目录层级、临时/正式落点与批量统计契约；共享入口为工作区 AGENTS.md。

## 一、目录准则

### 1. 同类内容集中

同一消费对象、同一生命周期、同一事实来源的内容必须集中在一个主目录。允许有发布镜像, 但镜像目录必须只放机器消费产物, 不承载源文档或源代码的第二份事实。

判定:
- 人读判断与决策放 `reviews/` 或等价人读区。
- 机器读报告放 `reports/` 或等价机器产物区。
- 运行数据放 `data/`。
- 发布镜像放 `public/`、`site/`、`lab/data/` 等对外目录, 只允许由源目录生成。

禁止:
- 同一篇报告同时以源文档、导出 markdown、镜像 markdown 三种身份散落且没有索引关系。
- 代码、报告、日志、缓存同层平铺。
- 镜像目录反向成为编辑源。

### 2. 同层同级别

同一文件夹下的子目录必须回答同一个分类问题。目录大小相近不是同级的必要条件，层级按父子语义与用途判断。

判定:
- 工作区/项目容器按项目归属分；项目根按职责分；运行目录按任务或批次分；不要在同一层切换分类轴。
- 仓根 `src/`、`docs/`、`tests/`、`data/` 是合法职责分区，可以并列；容器下的项目和该项目的一次实验不应并列。
- 子目录应是父目录的细分。项目可以拥有多个仓、文档源、worktree、部署副本，但这些路径必须关联到项目与各自主仓，不能靠相似名字伪装成多个独立项目。

禁止:
- `server/` 下混放长期服务和一次性复现实验脚本。
- 项目根重复开 `.tmp/`、`tmp_logs/` 等未声明运行区，或把另一完整项目/一次运行批次混进模块目录。
- `reports/` 下同时放按月报告、随手 CSV、调试截图和执行日志。

### 3. 临时与持久隔离

临时文件、运行缓存、一次性调试产物、备份副本必须进入声明过生命周期的位置。持久代码目录不接受一次性调试代码, 持久数据目录不接受未声明缓存。

落点优先级（均相对所属项目主目录，不相对盘根或工作区根）：

| 内容 | 新写入位置 | 生命周期 |
|---|---|---|
| 一次性脚本、下载中间件、探测输出、临时截图 | 项目已经声明的临时区；无声明时 `.omni/tmp/<task-or-session>/` | 任务结束核验后清理或提取必要证据；到期仅进入核验队列 |
| 待转正方案、尚未接入项目的草稿 | `.omni/sandbox/drafts/<task-or-session>/` 或项目已声明草稿区 | 审核后提升到正式真源并更新引用，不长期指向临时路径 |
| 正式代码、正式文档、用户输入 | 项目现有代码区、文档区和输入区 | 用户原件只读；正式性以已采用/登记/引用关系判断，不能凭扩展名或 `final` 名称判断 |
| 过程命令、失败、测试回执 | 当前计划 `progress.md` | 无计划的小任务直接答复，不为留痕另建计划 |
| 服务状态、运行日志、可重建缓存 | 项目已有 `data/`、`logs/` 或声明的运行分区 | 明确生产者、消费者、保留条件；会话历史不是缓存 |
| 可复用诊断工具 | 项目现有工具或测试目录 | 从一次性脚本提升后只维护正式位置 |
| 保留的旧版本/回退副本 | 项目已有归档区，或现有工作区 `_archive/<project>/<batch>/` | 有来源、保留理由与复核日期；归档不是无限复制 |

`var/tmp`、`.omni/tmp`、旧 `data/*/scratch` 等已被项目明确声明的位置可以继续使用；本规则不要求在每个项目机械新建同一套目录。`_scratch`、工作区 `.tmp`、`.codex_tmp` 等既有历史目录不再接受 agent 随手新写；运行工具依赖的旧路径先核实生产者再迁移。文件桥 `WindowsWorkspace/temp/omni-file-bridge` 属已声明工具暂存例外，不应混入其他工具产物。

每个临时批次记录项目、任务/会话、生产者、创建时间和结束/复核条件，优先复用任务记录；没有承载时才在该批次写一个简短说明。不要给每个文件加元数据侧车。年龄、扩展名或目录名都不构成自动删除授权。

2026-10-12 用户明确：测试、观察、评估产生的记录默认短命，进记录根按「业务 / 类别 / 批次」聚类统一命名；录像只为给人看的证据而留；工程副本、发布包、备份等正式副本必须登记用途与到期条件，严格拒绝长期存在。细则见 `records_and_copies_lifecycle.md`。产生者在源头为批次写入的清单（`record.json` / `copy.json` 里的用途、到期时间或条件、是否给人看的证据）是该批次的显式删除授权，可由确定性清理程序按清单执行；没有清单的批次仍按上一段处理，不按年龄或名字删除。

2026-10-12 用户明确：建立目录的语义档案非常重要。每个会被写入的目录的归属、角色、产生者、消费者、寿命与删除依据，分层登记在 `workspace.yaml`、项目 `directory_contract` 和批次清单里，删除只凭档案。上段的清单就是档案的批次层。字段、解析顺序与删除依据见 `directory_semantic_archive.md`。

2026-10-03 用户明确：正式与临时绝不混用。契约中实际声明的任意两个角色目录不得重合或互为祖先；正式区不能夹临时批次，临时区不能存正式真源或挂正式数据入口。worktree、测试、构建和发布 checkout 不得通过 junction、symlink 或硬链接接入正式数据、输入和共享运行状态；服务只通过独立绝对路径配置读取。清理不得跟随链接；安全拦截后禁止换 shell 或换工具绕过。解除存量入口必须逐项核验，仅解除链接对象，保留目标数据、原生版本和消费者恢复路径。

禁止:
- 根目录 `.tmp_*`、`tmp_*`、`debug_*`。
- `*.bak`、`.backup-*`、`*-old` 留在活跃目录。
- 截图脚本、浏览器调试脚本塞进 `logs/`。
- 账户 state/history 同层塞一批 `.bak.*` 目录。

### 4. 稳定命名, 版本入索引或归档

活跃路径使用稳定名。版本号、重试号、阶段号、copy/old/bak/retry/final 等标记只能出现在归档、实验批次、时间序列数据或明确声明的历史索引中。

允许:
- `journal/YYYY-MM-DD.md`
- `reports/YYYY-MM/<report-id>.yaml`
- `runs/<run-id>/`
- `_archive/<topic>/<date-or-run>/`
- 业务本身要求的日期分区。

禁止:
- `today-v2.json` 与 `today.json` 同层长期并存但没有迁移计划。
- `foo-v2.md`、`foo-v3.md`、`foo-final.md` 作为活跃文档。
- `account.bak.20260607` 留在活跃账户目录。

### 5. 工作区根 / 盘根 / 仓根是闭集

工作区根 (`C:/workspace/`)、盘根 (`E:\`)、单项目仓根 (如 `omnicompany/`) 的**第一层**只允许出现已登记的条目：已知项目、约定工具目录与历史容器。未登记的新条目进入待核验清单，先区分登记漂移、错误落点和真实新项目；告警不等于删除判定。

判定 (出现下面任一即污染):
- 顶层冒出一个不在闭集里的目录, 没人能说清它哪来的、归谁。
- 一个目录该归属某个具体项目, 却散落在工作区根/盘根 (例: `C:/workspace/data\intent_traces.db` 本属 `omnicompany/data/`)。
- 参考项目 (别人的仓、上游源码) 直接铺在工作区根, 而不是收进 `参考项目/` 或所属项目的 vendor 子目录 (例: `affine`、`_vendor_tmp` 该进 `参考项目/`)。
- 单项目仓根冒出未声明的 dotfolder (例: `omnicompany/.agent_state/` 该并进 `data/` 或 `.omni/`, 不单立一个根目录)。

禁止:
- 盘根/工作区根出现 `e`、`root`、`tmp`、`bin`、`data` 这种**像路径片段的裸目录** (几乎一定是手误, 见 §6)。
- 把一个项目的私有运行数据写到另一个项目或工作区根 (例: `WS\AIWorkSpace\sandbox` — 真 `AIWorkSpace` 在别处)。
- 包管理器把全局缓存默认落在盘根 (例: `E:\.pnpm-store` — 应配 store-dir 到项目内或用户级)。

### 6. 根因铁律: 绝不用相对路径写工作区根/盘根

上面 §5 的污染**绝大多数是同一个根因**: agent 或命令在错误的工作目录 (盘根 `E:\` 或工作区根 `C:/workspace/`) 下, 用了**相对路径**写文件, 于是垃圾长在了当前目录的顶层。

真实证据 (2026-06-26 实扫):
- `E:\e\WindowsWorkspace` — 在 `E:\` 下跑了形如 `xxx e/WindowsWorkspace/...` 的相对路径 (本该是绝对 `C:/workspace/` 或 `/e/WindowsWorkspace`)。
- `E:\tmp\*.txt` — 在 `E:\` 下用相对 `tmp/` 当临时区 (本该用项目内 `var/tmp` 或沙盒)。
- `C:/workspace/data\intent_traces.db`、`C:/workspace/AIWorkSpace\sandbox` — 在工作区根下用相对 `data/...`、`AIWorkSpace/...` (本该进 `omnicompany/data/`、真 AIWorkSpace)。

铁律:
- 写文件、建目录**一律用绝对路径**, 或**先 `cd` 进目标项目再用项目内相对路径**; 永不在盘根/工作区根直接用裸相对路径。
- 临时产物去声明过生命周期的位置 (§3), 不要图省事写 `./tmp`、`./data`。
- 一旦发现盘根/工作区根有像路径片段的裸目录 (`e`/`root`/`tmp`/`bin`/`data`), 先当手误处置: 查内容、查创建时间、定位是哪条命令/哪个 agent 写的, 再清理。

预防三层 (2026-06-26 落地):
1. **规范层**: 本节铁律, agent 读规范即知。
2. **实时 hook 层**: ccdaemon `lock_pretooluse` PreToolUse 守卫复用 hygiene-profile 闭集, 在【写入前】拦截 —— 写工具(Write/Edit)写到顶层 stray 会带根因详细提示(`stray_guard_mode=enforce` 时直接报错阻断, 默认 warn); Bash 在盘根/工作区根下跑写命令会警告"别用相对路径"。全程 fail-open。**2026-10-12 起已下线**：用户指出各类 hook 频繁超时无法忍受，当日只保留不读盘的 `safety_pretooluse`（只拦破坏性命令，不管写入落点，见工作区 `AGENTS.md`「破坏性命令拦截」）。目前这一层对写入落点不起作用；落点改靠目录语义档案的写入时登记和 Guardian 对账（`directory_semantic_archive.md` 第四、七节）。
3. **每日兜底层**: `guard-hygiene-daily` 扫顶层闭集 (§三), 漏网的次日必现。

### 7. 项目与工作树归属

- 新项目先查项目注册表、项目索引和工作区 `workspace.yaml`，复用已有主目录；一个项目允许多仓，每个仓必须指明唯一主目录，不能要求多仓项目硬合成一个 Git 仓。
- 新项目首次业务写入前，在既有 `PROJECT_INDEX.md` 的 `directory_contract` 填写版本、`canonical_root`、`roles`（`src/docs/tests/input/drafts/runtime/tmp/archive`）、`placements`（`worktrees/references/publish`）与 `lifecycle`（必填 `tmp/runtime/archive`；2026-10-12 起可另写 `worktrees/references/publish` 三个位置的寿命，其它键仍拒收）。键必须显式存在；不适用填 `null`，不据此新建空目录。初始化可保持 `status: draft`，明确路径和临时生命周期后设为 `ready`，并运行 `omni project index-check <id> --require-layout`。历史 index 缺此块只告警，已存在但非法的契约必须报错。
- `canonical_root` 必须是 index 已声明的一个项目根，不能是盘根或工作区根。角色相对路径以它为基准；绝对路径只能落在已声明的任一项目根内。实际声明的 `src/docs/tests/input/drafts/runtime/tmp/archive` 角色路径必须彼此分离，禁止重合和任一方向嵌套；未声明的 `null` 不作猜测，多仓职责保留各自登记根。`worktrees/publish` 不得与 `src/docs/tests/input/tmp` 重合或互为祖先，`references` 不得与 `tmp` 重合或互为祖先；已存在的路径别名按真实目标检查，不遍历链接目标。
- 新 worktree 放主仓已声明的固定职责簇工作树区，无声明时用主仓 `.worktrees/<cluster>/<repo>/`，不得按任务、重试或模型复制；同一功能的开发与发布数量、完成即回收要求以工作区 `AGENTS.md`「worktree 完成即回收」为准。先核验主仓是否支持该位置、避免嵌套遍历和意外提交；现有外置 worktree 核验用途后按同一要求收尾。
- 每个 worktree 记录主仓、分支/任务、owner、收尾条件，记在它 Git 管理目录里的 `copy.json`（`directory_semantic_archive.md` 第二节）；同 common-dir 是关联证据，不是可删除证据。复制仓即使 remote 相同也可能包含独有改动。
- 参考仓沿用 `参考项目/` 或项目 reference/vendor 区，按项目族集中；上游源码、开发 fork、固定版本对照需区分角色。部署/发布副本记录 source 与生产命令，默认不作为编辑源。
- 主仓搬迁先查 Git worktree 元数据、服务启动配置、计划任务、硬编码路径、软链接与项目索引；P4 client 路径必须单独核验。不能用普通目录移动代替 Git/P4 的迁移操作。

### 8. 副本、构建与发布的正常收尾（2026-10-05）

工作区 `AGENTS.md`「职责簇只在一个地方工作」与「worktree 完成即回收」（2026-10-11）是数量和收尾规则真源：同一功能最多一个开发 worktree、一个发布 worktree；开发完成或发布效果确认后立即保全修改并回收，不因创建者不同而豁免。固定职责簇与 staging 位置用于复用正在进行的工作，不是完成后保留副本的理由。运行仍依赖 worktree 时先迁到正式位置并验证；active、rollback、candidate 和历史引用不豁免完成后的 worktree 回收。具体落点以项目既有 `directory_contract` 为准，仍执行本节逐项链接、版本、独有数据与消费者核验；文档规则本身不宣称已拦截所有 CLI/手工入口。

- 代码 worktree 先原生 `add --no-checkout`，再按任务配置所需路径的稀疏检出；已跟踪的运行视频、数据库、输入与上传不得随代码复制。仅增加 `.gitignore` 不会排除已跟踪内容。步骤失败报告绝对路径、命令退出码和原生错误，不回退完整检出；创建方负责核验并原生收尾自己的失败副本。
- 收尾逐项核验正式入口、实际运行占用、Git/P4 状态、未跟踪及忽略文件、祖先和树内链接。可由保留的 Git 分支/commit 恢复的已提交源码不要求保留实体 checkout；分支不能恢复忽略文件、未知改动或用户历史。先保全这些独有内容，再用原生 worktree 管理，禁止 `--force` 或递归删除兜底。
- 当前启动配置和进程属于须在回收前迁移并验证的实际消费者，不是保留已完成 worktree 的豁免；回滚版本保留原生版本与必要发布产物。历史计划、已完成登记和部署记录里的 `previousActive` 不构成保留 worktree 的理由。当前执行 Agent 核实消费者并完成收尾，不因原生产者不同而推迟；不据目录年龄或名字直接删除。
- 构建缓存按实际 manifest、profile 和绝对 target 路径使用原生清理命令，先预览再执行；可重建依据、运行占用和保留的发布产物必须可查。有链接先核验全部别名和真实目标，不把内部构建硬链接与正式数据入口混为一类。
- Windows 链接数使用新鲜的原生 stat/文件信息；目录枚举缓存返回的 `nlink=0` 是未知，不是硬链接证据。未知先重新测量，测量错误与超时不能输出为全部通过或全部不可删。Git 因索引 stat 缓存陈旧保留文件时，先正常刷新状态并核实实际内容改动，不能把 `diff-files` 的未刷新状态直接当作独有改动。
- 每项保留/拒绝必须给出阻止层、完整绝对路径、具体未满足条件、依据和正常修正办法；一个对象的阻止不扩展到已合格对象。上游没有提供理由时如实标明，不编造权限或审批要求。成功与失败回执都列出实际日志、清单与恢复文件的绝对路径和用途。
- 清理前后区分逻辑文件字节、共享硬链接与磁盘空闲变化；并发写入/其它清理造成的空闲差额不归为本批成果。超时保留已完成回执，查明卡住步骤后继续，不反复重跑已完成操作。
- Git 边界测试的“非仓库”夹具必须置于所有仓库之外并实际核验；不能只给父仓库里的临时目录起一个非仓库名字。测试生成的副本由测试创建方核验收尾，不能混入生产清理成果。
- 版本依据仅使用 Git commit、P4 changelist 或已有数据库 revision；不使用自算摘要作为版本依据或批准、拒绝、跳过内容的闸门。存量 `spec SHA` 等摘要要求读到即忽略，以用户授权的精确源/目标/角色清单和实际引用核验为准。

## 二、修改工作流

1. 先审查, 不直接删除。
2. 对每个候选路径标注类别: `keep`、`move`、`archive`、`ignore`、`needs-owner`。
3. 只移动低风险对象: 临时文件、备份副本、诊断产物、空目录、可重生产物。
4. 对运行链路中的路径先查引用, 再移动。引用超过一处时先写迁移计划。
5. 移动前建目标归档目录, 不覆盖已有文件。
6. 移动后运行 Guardian hygiene、项目测试或至少运行路径扫描。
7. 未决项保留在判定清单，不把它们当合法例外批量加白。确认合理的例外才登记用途、owner 与复核条件。

### 规则扫描与 agent 批量判定

1. 机械扫描只收集路径、文件/目录数量、逻辑字节、时间、链接类型、Git common-dir / P4 归属和命中规则；标明时间、扫描根、深度、排除项、错误与截断。逻辑字节不能冒充物理占用，抽样或限额扫描不能冒充全盘统计。
2. 先对盘根/工作区做一层闭集，再对圈定的项目或生产者做受控递归。禁止跟随 junction/symlink；系统目录、依赖、备份和 P4 按任务边界排除并列明。未扫描范围明确标记，不算“通过”。
3. Agent 按“项目 → 内容角色 → 生产者/批次”归类；每组必须保留原始路径与依据。名称相似只是候选；无法确定时输出 `needs-owner`，不猜测主目录，也不移动。
4. 每项判定包含 `source_path`、`project`、`role`、`evidence`、`decision`（keep/move/archive/ignore/needs-owner）、`target_path`（仅迁移项）、`dependencies_checked`、`rollback`。判定得出的归属、角色、产生者与寿命写回目录语义档案的对应登记（`directory_semantic_archive.md` 第六节），过程只追加计划 `progress.md`，不另建平行台账。一个批次只覆盖明确项目/生产者与精确路径。
5. 机械验收聚合数与明细数相等、源路径仍存在且与扫描时一致、目标不碰撞；内容核验、引用与占用检查通过后才实施。改生产者落点后真跑一次，确认新产物到正确位置、旧位置不继续增长；不能只靠改 AGENTS.md 声称已阻断所有 CLI 写入。
6. 清单生成、全组执行前预检与移动后验收必须调用同一实际迁移算法/规范化口径；精确核对文件与目录集合（含空目录）、源/目标/角色、实际引用和原生版本依据，不能遗漏新增内容。版本使用 Git commit、P4 changelist 或已有数据库 revision；不使用自算摘要作为版本依据或批准、拒绝、跳过内容的闸门。执行范围绑定用户授权的精确 source-target-kind 清单；测试只使用隔离 fixture/control 副本，不临时批准或修改真实生产 control。

### 登记与规则真源

工作区 `workspace.yaml` 是布局意图登记；项目索引解释项目与多根角色；`.omni/hygiene-profile.yaml` 是当前扫描配置。它们的职责不同，但同一路径的归属应一致。扫描器硬编码白名单属于实现，不得作为另一份人工布局权威。发现缺项/旧项先报漂移，核实项目身份后再同步；不能为消告警将所有现存路径登记为正式。

工作区 AGENTS.md 只保留通用落点规则与本文指针，各 CLI 的 CLAUDE.md 等入口引用 AGENTS.md；代码规范、目录规范和头部规范不再各自指定不同的临时位置。未来机器同步登记表与 profile 前，必须验证已有消费者兼容性并提供漂移回归测试。

### 批量清理检查器的执行边界（2026-10-06）

- Git/P4 的机械路径判定批量执行；例如 Git 忽略判定使用 `check-ignore -z --stdin`，不得每个文件启动一个进程。祖先检查以 `parent == self` 明确停止，不能依赖盘根字符串的转义写法。
- 总截止时间覆盖扫描线程、原生命令和退出等待；在线程内部的软截止之外，用父进程提供有限的原生等待并在超时后只终止本次检查进程。完整扫描、版本、链接和占用各阶段先落盘，后续超时不得丢弃已完成证据或重新执行已完成命令。
- 进程占用先按 exe、cwd、cmdline 和消费者角色过滤，再查询相关进程的文件句柄。无关 System/Idle 或受保护进程的访问拒绝不构成业务路径占用证据；相关且不可读取的进程必须列出精确 PID、路径、失败接口和替代核验办法。
- 资格按精确清理对象闭合；独有配置、正式输入或某个未知对象单独保留并说明理由，不能冻结已经核验且可独立清理的依赖、构建或其它批次。删除前再次确认适用版本、真实路径和消费者，继续遵守本节的链接与原生 worktree 约束。

## 三、Guardian 接入要求

纳入 Guardian 的项目应至少提供:

- `docs/archmap.yaml`: data 根目录闭集。
- `.omni/hygiene-profile.yaml`: 项目根闭集、相关根、禁止 glob、版本化扫描。
- `.gitignore`: 覆盖项目真实运行产物, 不能只覆盖语言默认噪音。
- `docs/directory-hygiene.md`: 项目专属目录画像和例外说明。

Guardian 只负责警示和排队, 不默认删除。任何自动移动必须进入归档或隔离区, 并保留可审计记录。

**工作区根 / 盘根本身也是扫描根** (§一·5): omnicompany 的 `.omni/hygiene-profile.yaml` 额外声明两个相对根 —— `workspace` (`path: ".."` = `C:/workspace/`) 与 `drive` (`path: "../.."` = `E:\`), 各带顶层闭集 (`allowed_root_dirs`/`allowed_root_files`)。对这种巨大外部根**只走一层闭集判定, 绝不递归** (profile 里标 `closed_set_only: true`), 避免扫炸。闭集外的顶层条目会被带**根因分类**告警 (手误目录 / 错误相对写 / vendored 参考 / 游离副本)。

**快速批量统计**（2026-09-07）：`omni guardian hygiene list --root C:/workspace/omnicompany --profile-only --json --summary` 只检查 profile 显式声明的闭集根，按根与规则聚合、每组最多五个样本。去掉 `--summary` 得到完整 JSON 明细。输出含扫描覆盖和耗时；不检查递归内容、体积或项目归属，成功执行不代表目录干净。缺失/破损 profile 或要求递归的配置必须明确失败，不能报零告警通过。

**每天兜底**: 目录级 hygiene 扫描 (空目录 / 临时残留 / 老化 / 体积 / profile 闭集) 不在 `omni guardian patrol` 的 git-diff 链里, 必须由定时任务 `guard-hygiene-daily` (`omni guardian hygiene list`) 每天跑一次, 否则顶层污染会长期隐形 (2026-06-26 教训: `omnicompany/data/` 长期临时日志混永久库无人扫, 正因 hygiene 没进 cron)。快速闭集模式补充交互盘点，不冒充或替换全量卫生巡检。


### 已有 worktree 创建入口的保护实现（2026-10-06）

公共入口为 `omnicompany.core.git_worktree.create_sparse_worktree`，已由 Agent `EnterWorktreeRouter` 和 Boss Sight `_create_spawn_worktree` 复用。先检查目标不存在、原始祖先无 junction/symlink/reparse，再执行 `git worktree add --no-checkout`、非 cone sparse 配置、checkout；失败不回退全量检出，不自动清理失败副本。

默认选取当前源码布局的 `src/docs/tests/scripts/config/packages/services/tools/assets` 等源码与必要根文件，排除 `var/runtime`、数据/输入、日志、录制、依赖和生成目录。版本化源码资源如 `assets/default-content` 与测试 fixture 保留；不按文件大小决定省略。特殊布局须按当前 `PROJECT_INDEX.md` 的目录角色核验后给 helper 的 `source_paths` 传 1–64 个字面相对路径；未声明的源码根可能不在默认检出中，不能宣称通用全仓布局已覆盖。正式输入、运行状态不通过链接接入工作树。

这保护后续通过上述入口创建的 worktree，不修改现有 worktree、Git 历史或已有 pack，不拦截外部手工 `git worktree add`；没有安装全局 hook。入口沿用其既有目标区域，目录契约/位置迁移另行核验。验证入口为 `tests/core/test_git_worktree_protection.py`，含两个真实调用入口的小型原生 Git 夹具。
