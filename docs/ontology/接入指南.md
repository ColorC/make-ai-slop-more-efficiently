# 接入指南 · 把一个项目的决策/假设/计划接进本体套件

这是说明书(怎么操作),不是手册条目(怎么判断)——按收录范围它永远不进分册。
判断类问题(什么算显化决策/猜想何时晋升)以 [00-本体自述](00-本体自述.md) 与 [20-探索通则](20-探索通则.md) 为权威。

## 场景一 · 日常:工作中随手记(每个项目从第一天就该做的)

开工一次,绑定一次;拍板一笔,记一笔。不需要任何"接入手续"。

```
omni plan use <计划id>                                # 会话绑定(skill: session-self-bind)
omni decisions brief                                  # 开工切片:绑定后零参数自动出——本计划
                                                      # 已有拍板(先延续!)+该域条目+活跃猜想+近期偏离
omni decisions record --kind decision -s "选了X" \
    --choose "X:理由" --reject "Y:为什么否" -r "…" -p <project>   # 拍板必显化被否项
omni decisions record --kind belief -s "猜Z成立" --risk high --query "怎么验" -p <project>
omni decisions link <子id> rests_on <前提id>            # 推导必须带出处
omni decisions challenge/resolve <BLF-id> …             # 猜想有下场,不许烂在 untested
```

**该记什么**:改变后续做法的选型、方向、否决;可证伪的世界观猜想;用户拍板原话(anchor.excerpt)。
**不该记什么**:纯执行流水(进度去 whatnow)、性价比/环境约束类规则(留接口层)、能从代码直接读出的事实。

## 场景二 · 复杂综合决策(跨多轮对话的大裁决,如"重写世界观""换架构")

1. 过程中的每次子拍板照场景一记,`link parent` 挂到同一根决策下(分形树);
2. 尘埃落定后,若这个判断**会被反复用**(下次同类情况还按它办)→ 提议进手册:
   ```
   omni decisions candidate --action new --source human \
       --title "…判断方法" --statement "一句话结论" --body "按条目模板写草案" -p <project>
   ```
3. 用户裁决 → `omni decisions candidate-apply` 写回 → 编辑对应分册把草案落成正式条目 → `python scripts/sync_ontology_book.py`。
   **改手册没有第二条路**——直接编辑分册加新条目也允许(人是终审),但加完必须跑 sync,且重大新条目建议仍走候选留痕。

**裁决渠道(2026-07-10 用户定则,判例 DEC-2026-07-10-059)**:待裁决问题在**对话内**直接提出,用户在对话内答复即为裁决(原话记 anchor.excerpt);
审阅台是次要路径——主用于"看"(只收工作报告/对照稿类材料,禁把裸的待裁问题单独作为材料推上去),次用于明确需要交叉裁决的项目;
材料的 accept/reject 状态**不作为**用户同意与否的判据,除非附有较明确的用户评论。候选流水线仍是唯一写入通道(登记与留痕),但"人裁"信号以对话内答复为主。

## 场景三 · 新领域开分册(项目积累了成套判断方法时,照 vilo 样板)

触发条件:该域已有 ≥3 条真实判例(库内 DEC id)+ 有"怎么判"的稳定方法,不是一次性选型。

1. 新建 `docs/ontology/NN-<域名>.md`(NN 取空闲十位数),每个条目照 00 的**条目模板八栏**写,缺项写"暂缺";
2. 域有外部真源(如 vilo 的台账)→ 条目**引用不搬**,写清"领域真伪权威=<路径>";
3. 在 `domains/decisions/book.py` 的 `PART_META` 登记本分册的 project 与 authority
   (条目蒸馏自用户拍板=user_explicit,AI 归纳用户未逐条确认=high;sync 与 brief 切片共用这份单点);
4. `python scripts/sync_ontology_book.py` → 蒸馏态指针记录自动入库;
5. `omni decisions checklist NN-<域名>` → 生成交稿检查单;
6. `omni decisions patrol` 必须零违规(条目缺指针/判例假 id 都会被点名)。

## 场景四 · 管线接入(该项目有注册管线时)

给 `core/pipelines.py` 里自己的 `PipelineEntry` 补:
- `when={"semantic": "什么时候该跑", "match_keys": […], "judge": "rule|statistical|llm"}`
- `scale={"tier": "quick|short|long", "minutes": "…", "cost": "…"}`;长管线加 `confirm=True`(+`segments` 小段入口)
- `book_refs=("docs/ontology/NN-….md#条目名", …)` 指回消费的手册条目
之后 sync 会把管线自动回填进条目的投影列表;patrol 的 when 覆盖率报告会少一条缺口。

## 场景五 · 日常节拍(接入后系统自己转的部分)

- **按真实工作触发维护**: 偏离/到期复核走 `omni decisions candidates-scan`，已有足够新判例时再按需运行 `omni decisions consolidate -p <project>`；2026-07-22 起不再维持两条独立周 cron，也不为没有新工作量的项目制造候选。
- **留痕**:管线跑一次记一条 ledger 事件带 `consumed_decisions`(现成钩子=`ledger.provenance_hook.record_tool_run`,lint/config/前端管线已挂;新管线照抄一行);做法与陈述相悖时 `omni ledger deviate --ref <id>`——只报告,修订走候选;
- **回看**:`omni decisions brief`(按 plan/project/pipeline/keys 四轴切片)与 `find/recall/show`;驾驶舱项目页 canvas「决策」姿态看图;`docs/ontology/30-知识.md` 看猜想现状。

## 接入完成的验收(不看做了多少,看这五条)

1. `omni decisions list -p <project>` 有真实记录且拍板类带被否项;
2. 库内该域 belief 不全是 untested(challenge/resolve 在动);
3. 若开了分册:patrol 零违规 + 检查单能生成;
4. 若有管线:注册表带 when/scale,ledger 里有它的 consumed_decisions 事件;
5. 该项目出现过候选并被用户裁决过至少一次(裁决信号以对话内答复为主;审阅台通过/否决不算数,除非附明确评论)。
