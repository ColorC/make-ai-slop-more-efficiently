# Bilibili 网页投稿自动化探索（2026-07-17）

## 结论

Bilibili 的网页创作中心适合建立“本人账号、真实 Chrome、自动填稿与保存草稿、人工检查发布”的投稿助理。视频与专栏都有完整网页入口；专栏编辑器提供简单富文本、图片、链接、列表、引用、预览、草稿、定时发布、话题、文集、自定义封面和 AI 辅助创作声明。

Bilibili 也提供官方开放平台 API，覆盖视频稿件和专栏稿件的新增、编辑、删除、查询、图片上传及数据回流。但当前登录账号进入身份认证后，只能选择企业开发者，表单要求营业执照、企业申请公函和数据安全尽调问卷。因此，个人账号当前不能把开放平台 API 作为默认运输层；有合格企业主体时可另行申请。

## 当前网页实测

使用账号自身已登录的日常 Chrome 访问：

- 创作中心主页正常打开，没有出现验证码或风险提示。
- 投稿入口包含视频投稿、短剧投稿、专栏投稿、UP 动画、互动视频投稿。
- 视频网页上传显示：单文件 16 GB 以内、10 小时以内；粉丝数达到 1000 后可解锁 64 GB 文件。
- 专栏编辑器标题建议 30 字以内，正文上限 100000 字。
- 专栏工具栏包含撤销、重做、格式刷、清除格式、标题、小字、粗体、斜体、下划线、删除线、文字颜色、背景颜色、对齐、有序列表、无序列表、图片、链接、分隔线、引用、表情、扩展插入、导入和预览。
- 发布设置包含所有人可见、仅自己可见、自定义封面、评论开关、精选评论、定时发布、原创声明、AI 辅助创作声明、话题和文集。
- 定时发布范围为当前时间加 2 小时至 7 天。
- 页面存在明确的“保存为草稿”和“发布”按钮。

随后完成了一次真实草稿试填：把 Qwen 3.7 Max 已经写完的《AI写中文，改了六版还是不像人写的》原文按连续专栏格式写入编辑器，Agent tag 保持在正文第一行，四个 `01｜…` 章节转成原生二级标题，勾选“AI 辅助创作声明”，并点击“保存为草稿”。页面读回标题、正文、四个标题结构、Agent tag、AI 勾选状态和“保存成功”均一致；没有点击发布。

又完成一次可逆图片验证：将文章真实提到的量化页面截图通过系统剪贴板原生粘贴进编辑器，页面生成一个 `figure/img` 节点和图片注释输入框，图片数量由 0 变为 1。随即执行一次撤销，图片数量恢复为 0，正文 1570 个读回字符逐字恢复，四个二级标题、AI 声明与保存成功状态保持不变。测试同时发现 `Ctrl+End` 没有可靠移动到文末，图片落在旧选区位置，因此正式适配器禁止以文档末尾快捷键作为插图锚点。

## 官方能力

开放平台文档列出的能力包括：

- 视频文件上传预处理、分片上传、合片、封面上传、稿件提交、编辑、删除和查询。
- 专栏文章提交、编辑、删除和查询，文集管理，专栏图片上传。
- OAuth 2.0 账号授权、用户和稿件数据、沙盒环境、Webhooks。

官方文档明确说明稿件提交后进入审核，审核期间不对外开放。文章提交接口为 `POST /arcopen/fn/article/add`。

当前企业认证页要求：公司名称、公司网址、企业代码、公司地址、公司简介、联系人、身份证号码、邮箱、手机、营业执照、申请公函和数据安全尽调问卷。

## 自动化暴露面检查

仅使用专门面向浏览器自动化诊断的公开测试页，没有挑战验证码或访问受保护内容。

### Sannysoft Antibot

- WebDriver 新旧检测、Chrome 对象、插件、语言、WebGL、Selenium 属性等主要静态项通过。
- 页面观察到的是普通 Windows Chrome 环境，不是独立无头浏览器配置。

### Incolumitas Bot Detection

- 新检测组显示 WebDriver、Puppeteer/Playwright 常见注入、Worker 一致性和 stealth 插件检测为 OK。
- 旧检测组中的 `WEBDRIVER` 一项显示 FAIL。
- 行为分数未作为结论：本轮没有模拟浏览、填写挑战或提交表单。

### Device and Browser Info

同一台机器、同一网络下做了 A/B：

- 当前用于控制日常 Chrome 的扩展通道：`navigator.webdriver=false`、未命中 Playwright 和无头浏览器等常见标记，但命中 `isAutomatedWithCDP=true`，总结果为 `isBot=true`。
- 求职工具里的 Patchright 1.60.1 独立持久档：所有列出的静态项均为 false，包含 `isAutomatedWithCDP=false`，总结果为 `isBot=false`。

这说明旧求职方案的 Patchright 分支确实减少了公开测试页能够观察到的 CDP 自动化痕迹。它仍然不能证明 Bilibili 无法识别自动化，也不能抵消行为频率、账号状态、网络、设备和服务端请求模式等信号。

### 求职浏览器底座审计

- 主实现为 `scripts/job_apply/apply_driver.py`，采用可切换的 `playwright(channel=chrome)` 或 `patchright`，使用独立持久用户档，并通过本地 HTTP 命令服务执行导航、读取表单、填写、上传、下拉选择和截图。
- 当前安装的 Patchright 版本为 1.60.1，实际启动和公开诊断均可用，所以它不只是文档中的设想。
- 该底座没有自研指纹伪造、代理轮换、验证码处理或行为模拟。所谓“高隐身”主要来自 Patchright 对常见自动化痕迹的修补和独立持久档。
- 旧代码自己记录了 Patchright 在 OAuth、QQ、微信跨域跳转上可能崩溃；原版 Playwright + 真 Chrome 更兼容登录，但在本轮现代测试页中暴露了 CDP 控制信号。
- 可复用的是持久档、命令队列、表单原语、人工登录/验证码/发布边界和异常即停；Bilibili 需要自己的专栏结构读回、AI 标识、草稿保存和草稿恢复适配器。

这些测试只能说明静态自动化痕迹较少，不能证明不可检测。平台仍可根据行为频率、错误重试、上传节奏、账号状态和服务端请求模式判断异常。

## 推荐运输层

### 第一阶段：网页草稿助理

状态机：

1. `PREPARED`：本地包通过文字作者、事实、隐私、素材和格式检查。
2. `BROWSER_BOUND`：绑定本人日常 Chrome 与本人 Bilibili 账号。Patchright 仅保留为公开诊断对照，不承载默认草稿运输。
3. `EDITOR_OPEN`：打开视频或专栏正式网页编辑器。
4. `CONTENT_FILLED`：写入标题、正文、图片、封面和元数据。
5. `CONTENT_VERIFIED`：从网页编辑器读回标题、正文结构、图片数量和关键设置。
6. `AI_MARKED`：勾选平台的 AI 辅助创作声明并读回选中状态。
7. `DRAFT_SAVE_PENDING`：执行一次保存草稿。
8. `DRAFT_SAVED`：重新进入草稿管理页，确认草稿存在且内容可恢复。
9. `USER_REVIEW_REQUIRED`：停止自动操作，由 ColorC 检查并发布。

第一阶段不提供自动点击“发布”的操作。

### 第二阶段：官方 API

仅在开放平台企业认证和应用权限审核通过后启用。使用 OAuth 授权、官方签名、沙盒预演和最小权限；不复用网页 Cookie，不调用未公开接口。

## 稳定性与低异常约束

- 使用有界面的固定浏览器档、固定设备和正常网络，不启动无头配置。若使用 Patchright，采用专用持久档并只做低频草稿辅助，不迁移或导出日常 Chrome 的 Cookie。
- 不导出或读取 Cookie、Local Storage、密码和验证码。
- 不使用未公开网页接口、抓包重放、指纹伪造、验证码绕过或风控规避。
- 每个字段只允许一次主要操作；定位失败后重新读取页面结构，禁止原样高频重试。
- 使用稳定的语义、属性和网页编辑器结构定位，视觉坐标只作为最后手段。
- 上传与保存采用幂等任务 ID，避免同一素材反复上传和重复创建草稿。
- 遇到验证码、账号风险提示、登录失效、审核异常、页面结构未知或读回不一致立即停止。
- 保存草稿前必须完成 AI 标识读回；发布永远由人类执行。
- 留存本地回执：账号别名、稿件类型、源文件哈希、填写字段、读回结果、AI 标识状态、草稿 ID 或草稿标题、时间戳和停止原因。

## 与现有发布设施的关系

- 复用 `config/publication_common/production-copy-authorship.md`：全部公开中文由登记的 Qwen 模型独立成文。
- 复用 `config/publication_common/visual-evidence-and-layout.md`：优先真实截图、录屏和产品产物，并执行隐私检查。
- 复用小红书移动草稿的状态机、读回验证、风险提示即停、草稿回执和人工发布原则。
- Bilibili 另建渠道适配层，不把小红书的纯文本与 3:4 图卡限制带入专栏和视频。

## 当前实现

- 操作手册：`config/bilibili_publish/manual.md`
- Markdown 打包器：`src/omnicompany/packages/domains/bilibili_publish/markdown_package.py`
- 测试：`tests/bilibili_publish/test_markdown_package.py`

当前打包器接受 `title.txt + article.md`，输出按原文顺序排列的富文本片段、Markdown 图片、代码块/表格等格式图片、连续文档预览、运输 manifest 和 `browser-assembly.json`。装填合同要求第一段从正文起点开始，之后每段锚定上一条已经插入并读回的片段；禁止 `Ctrl+End` 与屏幕坐标猜测。它不继承小红书的篇幅和图卡限制，只保留 Bilibili 正文 100000 字的真实上限；标题超过 30 字只警告，不自动改写。Agent 成文会校验正文第一行的完整 Agent/Model tag，并要求后续运输勾选 AI 声明。

真实网页已验证标题、段落、二级标题、Agent tag、AI 标识、保存草稿、原生图片粘贴、图片节点读回和撤销恢复。下一项运输验证是从空白测试草稿按 manifest 交替装填全部富文本和图片，再重新打开草稿核对图片顺序与恢复结果；最终发布仍由人执行。
