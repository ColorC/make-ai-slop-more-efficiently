## 「策划设计文档门禁」是什么

这是一个命令行门禁，检查 AI 产出的策划细化案「写得像不像人类交付物」：图片是不是真嵌、命名有没有乱造、说明表在不在位、有没有 AI 味的占位符和自指旁白。它不判断设计本身对不对——数值合不合理、边界耦合完不完整，不在这个门禁的能力范围内，那部分要靠人审或系统组 doc_editor 的审查流程。

工具已经上架 AIWorkSpace，相对路径是：

```
app/tool/design-doc-lint/
```

也就是说，如果你的 AIWorkSpace 在 `D:\P4\main\AIWorkSpace`，完整路径就是 `D:\P4\main\AIWorkSpace\app\tool\design-doc-lint`（2026-07-07 上架，P4 change 1375165）。它只依赖 Python 3.10+ 标准库，不用装任何包，同事直接能跑。

## 与 doc_editor 的 gdd-review 是什么关系

系统组 doc_editor 的 gdd-review 是另一套独立开发的端到端文档生成与审查流水线，覆盖面更广，包含逻辑完整性、UI-规则-配置一致性等设计层面的检查。本门禁只做单点的交付卫生检查——图片、命名、说明表这类文档能不能被人继续协作、继续读下去的问题。两者互补而不冲突：可以在 doc_editor 产出细化案之后，再追加跑一遍本门禁，把文档卫生问题拦一道。

## 位置与启动

工具目录下有五个文件，跑门禁只需要进到这个目录，执行两条命令：

```powershell
cd app/tool/design-doc-lint
python lint.py <细化案.md> [--mode 协作|交付] [--json]
python semantic_review.py <细化案.md> --no-llm
```

- `lint.py`：十项确定性硬校验，秒级出结果。
- `semantic_review.py`：命名语义审查，默认 `--no-llm` 走纯确定性扫描。

`--mode` 区分文档所处阶段：`协作` 用于正在改的活稿（默认），`交付` 用于给下游消费的定稿；两种模式都要求「未定的不装定」——有待定标记时必须收拢进未决章节，不许把待定项藏起来假装写完了。`--json` 让 `lint.py` 输出结构化结果，方便脚本或 AI 解析。

## 文件结构

| 文件 | 干什么 |
|-|-|
| `lint.py` | 十项确定性硬校验：图链真实、禁非 mermaid 框图、完整说明表在位、公式带算例等，纯正则和文本解析，不调模型 |
| `semantic_review.py` | 命名语义审查：三层网（登记名 / 权威词表 / 叫法一致性），默认 `--no-llm` 只跑前两层的确定性扫描 |
| `lexicon_build.py` | 权威词表构建器，从本工作区 wiki / 配表 csv / 代码 lua 三源确定性抽取项目惯用名 |
| `lexicon.json` | 已构建好的权威词表，随目录自带，1035 条名字、来自 wiki frontmatter、配表显示名、代码文案三个源 |
| `README.md` | 面向开发者的简要说明，命令、用法、出处都在里面 |

词表不是实时抓取的，是一份构建好放在目录里的快照。项目功能持续在变，词表会过期；发现词表外误报明显变多时，用 `lexicon_build.py` 重新跑一遍构建即可刷新 `lexicon.json`。

## 使用方式

完整的一次使用，建议按这个顺序走：

1. **写完细化案**：正常写策划细化案 Markdown。
2. **跑 lint**：`python lint.py <细化案.md>`，按输出的 FAIL 清单逐条改——每条 FAIL 都带行号和原因，比如「图链文件不存在」「公式无同小节算例」。改完可以重复跑，直到 FAIL 清零（WARN 不必清零，是提示性的）。
3. **跑语义审查**：`python semantic_review.py <细化案.md> --no-llm`，处理"建议统一"一类的发现——这类通常是同一个东西在文档里被叫了两个名字，需要人决定统一到哪个，或者显式声明这是新概念。
4. **（可选）交人审**：文档卫生过关之后，可以再交给同事或 doc_editor 的 gdd-review 走设计层面的审查。

## 原理

`lint.py` 做十项确定性判据（判法权威见「细化案展示逻辑手册」第三部分）：

1. 图链真实
2. 禁非 mermaid 框图
3. 完整说明表在位
4. 公式带算例
5. 禁符号串正文
6. 一级章节轴
7. 禁自指与生产史旁白
8. 决策带理由（只 WARN）
9. 工作态（禁角色派工、未决收拢）
10. 开头定位句

`semantic_review.py` 是语义三层网：

- **第一层·登记名**：以文档自己的登记表为锚，机器穷举文中疑似缩略或近似变体的叫法。
- **第二层·权威词表**：拿 `lexicon.json` 当白名单裁判，抓正文混用多个真名、或字面走样成词表外名字的情况。
- **第三层·叫法一致性**（可选 LLM 兜底）：对前两层扫出的嫌疑做语境确认，判断到底是不是同一个东西被叫了不同名字。这一层需要你自己的模型环境，默认 `--no-llm` 直接跳过，不影响主要能力。

## AI 结合的使用方式

把这个工具目录的路径（`app/tool/design-doc-lint/`）连同 README 一起交给 Claude 或 Codex 这类 AI 助手，让它在生成或修改细化案之后自动跑两个检查器，再按 FAIL 清单和发现列表自己修正。`--json` 输出的结构化结果方便 AI 解析、逐条定位到行号处理，不用人工去读终端文本。

## 验证状态与局限

判据在公会对决这个功能的样本上做过红绿基线和种错测试：红样（人为写坏的测试文档）跑 `lint.py` 拦下 7 项 FAIL，`semantic_review.py` 语义审查跑出 40 多条发现；这说明确定性判据和语义扫描本身是能抓到问题的。

但还没有的验证：

- 还没有在一个真实的新需求上从头走过一遍——目前所有验证都基于公会对决这个老功能的改写与反推样本，不是从零开始的真实案例。
- 语义审查里的 LLM 兜底确认层，在这次上架的独立版本里还没有单独验证过；默认 `--no-llm` 路径（纯确定性扫描）是已验证的部分。
- 设计判断从来不在这个门禁的能力范围内：过度配置、该不该加某个机制、边界耦合是否完整，仍然要靠人看，或者配合 doc_editor 的 gdd-review。

### 实现历程与艰难程度

2026 年 7 月 4 日前后，命名审查补入词表白名单。这里卡住的不是技术形式，而是误报与漏报边界：短称、别名、显示文案、机制名、普通描述混在一起，不能把所有「不在文档登记里」的词都当错，也不能把疑似错名自动登记。最后采用的方式是分层处理：机器先召回，模型只在需要时确认，人处理高风险项。

2026 年 7 月 7 日，工具从私有工作环境剥离，上架 AIWorkSpace 成为独立可跑的五文件目录（README.md / lint.py / semantic_review.py / lexicon_build.py / lexicon.json），只依赖标准库，同事不需要额外环境即可直接使用。

### 实际使用成果

2026 年 7 月 5 日重录后的基线里，红样为 7 FAIL，裸改红样为 5 FAIL，带手册一遍稿为 4 FAIL，循环修复绿样为 0 FAIL，种错红样为 3 FAIL；代码反推验证稿为 0 FAIL。语义审查在同一批红样上跑出 40 多条发现。

## 还没验证 / 局限

这个门禁目前只适合检查 AI 产出的 Markdown 细化案。collab platform导出的原生格式、图床 token、原生提及构件会带来假失败，不适合作为直接输入。

设计判断不在门禁能力内。过度配置、该不该加某个机制、边界耦合是否完整，仍然要人看；门禁只能把文档层面能先拦的错误拦出来。

词表覆盖还会随功能变化。新功能接入时需要重跑 `lexicon_build.py` 采该功能真源重建词表，否则词表外误报偏高。

语义审查里只要打开模型确认，就存在结果波动。验收场景里更适合跑两次取并集，再由人处理高风险项。确定性检查没有这个问题，但它也只能检查规则覆盖到的部分。

目前所有验证都基于公会对决这个老功能的改写与反推，还没有在一个真实新需求上从头走过一遍；上架 AIWorkSpace 的独立版本本身，也还没有单独跑过一轮完整验证。
